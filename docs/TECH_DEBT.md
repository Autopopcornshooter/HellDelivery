# TECH_DEBT.md

이 문서는 **현재는 문제가 아니지만** 프로젝트가 성장하면 개선이 필요해질 내용을 기록한다.

**역할**: 나중에 개선할 것. 지금 당장 고장난 것은 `KNOWN_ISSUES.md`에 기록한다. 이 문서의 항목은 버그가 아니다 — 지금 상태로도 MVP-1은 정상 동작한다.

---

### TD-001 — 디버그 로그 제거

`Player.gd`의 `_detected_package`(`# DEBUG` 표시)와 `"Package detected"`/`"Package lost"` `print()`는 T041에서 감지 로직을 확인하기 위해 추가되었다. 정식 빌드 전 제거하거나, 필요하다면 로깅 시스템으로 정리한다.

### TD-002 — 물리 파라미터가 체계적 설계가 아닌 실측 재탐색으로 결정됨

`push_force`(8.0 → 40.0 → 220.0) 등은 질량/마찰/댐핑 공식에서 역산한 것이 아니라 여러 값을 실측 테스트하며 목표 체감(밀림 거리)에 맞춰 경험적으로 조정되었다. 콘텐츠가 늘어나(예: 여러 종류의 택배, 서로 다른 질량) 값이 더 많아지면, 질량/마찰 기반 공식으로 자동 계산하는 방식을 검토한다. (`throw_impulse_strength`는 T071에서 고정 Throw 자체가 제거되며 함께 삭제되었다 — TD-012 참고.)

### TD-004 — 프로토타입 레벨 지오메트리를 정식 레벨로 교체 필요

`PrototypeLevel.tscn`의 지형(`Floor`, `Stairs`, `Ramp`)은 모두 `BoxShape3D`/`BoxMesh` 플레이스홀더다. 특히 계단은 실제 플레이 검증(T045) 중 발견된 문제(0.4m 단 높이가 걸어서 오를 수 없는 수준) 때문에 13단(단 높이 0.15m, 단 깊이 0.385m)으로 재작업되었는데, 이 수치는 "일단 통과 가능하게 만든" 값이지 미술적으로 다듬어진 정식 계단 형상이 아니다. 정식 맵(v0.5.0 Content Expansion) 제작 시 처음부터 아트/레벨 디자인 기준으로 재설계해야 한다.

### TD-005 — 리소스가 씬 파일에 인라인으로 정의됨

`Player.tscn`, `Package.tscn`, `PrototypeLevel.tscn` 등의 `CollisionShape3D`/`MeshInstance3D`에 쓰이는 `BoxShape3D`, `CapsuleShape3D`, `BoxMesh` 등이 각 씬 파일 내부에 `sub_resource`로 인라인 정의되어 있고, 별도의 재사용 가능한 `.tres` 리소스 파일로 분리되어 있지 않다. 씬 수가 적은 MVP-1 단계에서는 문제가 없지만, 여러 종류의 택배·여러 레벨이 같은 형태를 공유하게 되면 공통 리소스로 추출하는 것을 검토한다.

### TD-007 — 성능 최적화 미실시

현재 씬 규모(노드 수, 물리 바디 수)가 작아 성능이 문제된 적이 없어 별도 최적화를 하지 않았다. 콘텐츠가 늘어나면(여러 Package, 정식 맵, 온라인 동기화) 프로파일링과 최적화가 필요해질 것이다.

### TD-008 — 헤드리스 검증 스크립트가 임시 파일로만 존재

개발 과정에서 사용한 헤드리스 `SceneTree` 기반 검증 스크립트(`_tmp_*.gd`)는 매 작업마다 새로 작성하고 확인 후 삭제하는 방식으로 운용되었다(`CLAUDE.md`의 임시 코드 정리 원칙에 따름). 재사용 가능한 회귀 테스트 스위트로 정리되어 있지 않아, 이후 변경 시 동일한 검증을 처음부터 다시 작성해야 한다. 프로젝트 규모가 커지면 정식 테스트 스위트 도입을 검토한다.

### TD-013 — Force-Based Physics Grab 물리값(T072)은 역산·추정값으로 시작했으나 사용자 승인으로 프로토타입 기준값(Baseline) 확정

`grab_spring_strength`(500.0)·`grab_damping`(60.0)·`max_force_per_grabber`(300.0)는 T044/T061처럼 여러 후보값을 헤드리스로 비교 실측하는 과정 없이, 각 오브젝트의 실제 mass×gravity(중력 저항력)를 근거로 "한 명은 Crate를 겨우 버티는 수준, 두 명이면 확실히 빠름"이 되도록 역산한 초기 추정값으로 시작했다. 헤드리스 자동 검증으로 "무게 순서가 올바른가(SmallBox>Package>Barrel>Crate)", "2인 협동이 실제로 더 빠른가", "관통·NaN·폭발적 속도가 없는가"까지는 확인했었다.

**사용자 승인(해결은 아님)**: `docs/TASKS.md` T072 "사용자 수동 테스트 승인(최종)"에서 무게 차이 체감, 중력·관성에 의한 출렁임, 모서리 grab 회전, 자연스러운 Release 운동량 등 "잡는 손맛"에 해당하는 항목들이 실제 플레이로 전부 승인되었다. 따라서 현재 수치는 **사용자 승인된 프로토타입 기준값(Baseline)**으로 확정한다 — T061의 "Baseline Freeze"와 같은 성격이며, 값 자체를 변경하지 않았다는 점에서 T068식 전용 수치 재검토(여러 후보 실측 비교)는 아직 거치지 않았다. 이 항목은 완료를 막는 미해결 결함으로 취급하지 않으며, 추가 수치 조정이 필요하다고 판단되면 T068과 같은 방식의 별도 Task로 진행한다. **T070(v0.2.0 최종 재미 검증)에서도 동일 항목(무게감, torque, Body Push 감각)이 다시 승인되어 v0.2.0 완료를 막는 요소가 아님을 재확인했다.**

### TD-014 — 게임패드 입력 감도/deadzone(T074)은 실측 후보 비교 없는 초기 추정값으로 시작했으나 사용자 승인으로 프로토타입 기준값(Baseline) 확정

`Player.gd`의 `gamepad_look_sensitivity`(2.5)·`gamepad_deadzone`(0.2)는 로컬 협동(T074)에서 Player 2(게임패드) 슬롯을 위해 새로 추가된 값으로, T044/T068처럼 여러 후보를 헤드리스로 비교 실측하지 않은 초기 추정값으로 시작했다. 헤드리스 자동 검증으로 "게임패드 입력이 실제로 이동/시점 회전을 일으키는가", "Player 1 입력과 서로 섞이지 않는가"까지는 확인했다.

**사용자 승인**: `docs/TASKS.md` T074 "사용자 수동 테스트 승인(최종)"에서 실제 게임패드로 조작해 정상 작동함을 확인했다. 따라서 현재 수치는 **사용자 승인된 프로토타입 기준값(Baseline)**으로 확정한다 — T061/T072와 같은 성격이며, 여러 후보를 실측 비교하는 T068식 전용 튜닝은 아직 거치지 않았다. 완료를 막는 미해결 결함으로 취급하지 않으며, T075(Local Co-op Interaction UX)에서 `move_deadzone`/`look_deadzone`으로 세분화되었다. **T075 사용자 승인**으로 분리된 두 값(각 0.2)도 동일하게 Baseline으로 확정되었다.

### TD-015 — T075에서 새로 도입된 게임패드 Grab 트리거값(`gamepad_grab_trigger_threshold`)·반전 옵션(`invert_gamepad_y`)은 실측 후보 비교 없는 초기값 (비차단, 튜닝 항목으로 유지)

`Player.gd`의 `gamepad_grab_trigger_threshold`(0.5, 오른쪽 트리거를 "눌림"으로 판정하는 임계값)와 `invert_gamepad_y`(오른쪽 스틱 상하 반전, 기본값 `false`)는 T075(Local Co-op Interaction UX)에서 P2 게임패드 Grab 입력을 트리거+A 버튼 OR 조합으로 확장하며 새로 추가된 값이다. 헤드리스 자동 검증으로 "트리거+A 동시 입력 시 중복 Connection·조기 Release가 없는가"까지는 확인했으나, 실제 트리거를 당길 때의 반응감(임계값이 너무 이르거나 늦은지)과 Y축 반전 기본값의 체감 편안함은 실측 후보 비교 없이 결정된 초기 추정값이다.

**사용자 승인(T075)**: `docs/TASKS.md` T075 "사용자 수동 테스트 승인(최종)"에서 현재 구현 상태로 승인되어 T075 자체는 `[DONE]` 확정되었다. 다만 이 두 값은 여러 후보 실측 비교를 아직 거치지 않았으므로, **완료를 막지 않는 비차단(non-blocking) 튜닝 항목**으로 계속 남겨둔다 — T068식 전용 튜닝(여러 후보 비교)이 필요하다고 판단되면 그때 별도 Task로 진행한다.

### TD-016 — 루트/메인 Viewport의 소량 중복 렌더링 (비차단)

T074에서 도입한 분할 화면 구조(`SplitScreen`의 `SubViewportContainer` 2개)가 화면 전체를 덮지만, 메인/루트 뷰포트 자체는 여전히 어떤 Player의 실제 `Camera3D`를 기준으로 별도 렌더링을 시도해 약간의 렌더링 낭비가 있다. 기능적으로는 화면에 영향이 없다(분할 화면에 완전히 가려짐). v0.3.0 완료를 막는 요소가 아니며, 성능이 실제로 문제될 때(`TD-007` 참고) 함께 검토한다.

### TD-017 — 3인 이상 로컬 협동 확장 시 시각 레이어(Visual Layer) 재검토 필요 (비차단)

로컬 Player Mesh 은닉용 시각 레이어를 T074에서 `player_slot` 기반 동적 계산으로 바꿨다(T073의 정적 하드코딩 대체). 현재 2인(slot 0/1) 범위에서는 문제없이 동작하지만, 3인 이상으로 확장할 경우(이번 범위 밖, `GAME_DESIGN.md`상 최대 4인 협동 목표) Godot의 시각 레이어 개수 제한(20개)을 고려한 재검토가 필요할 수 있다. v0.3.0(2인 검증) 완료를 막는 요소가 아니다.

### TD-018 — 온라인 멀티플레이 네트워크 동기화 미구현 (비차단, 범위 밖)

T072에서 다중 Grabber 물리 구조(`grab_connections: Dictionary`)가 도입되고 T074~T076에서 로컬 2인 협동으로 검증되었지만, 이는 **로컬 물리 구조에 한정**된다. 실제 온라인 멀티플레이에 필요한 네트워크 동기화(입력 전송, 권한 판정, 지연 보정 등)는 전혀 구현되어 있지 않다. `docs/ROADMAP.md`상 온라인 멀티플레이는 v0.3.0의 명시적 범위 밖(`Out of Scope`)이며, 이후 별도 버전에서 검토한다.

### TD-019 — Held Object Push 전달 상한값(`push_transmission_accel`)은 실측 후보 비교 없는 초기값이었으나 사용자 승인으로 프로토타입 기준값(Baseline) 확정 (비차단)

`GrabbableBody.gd`의 `push_transmission_accel`(12.0 N/kg)은 T076 재오픈 결함 수정(Held Light Object가 Heavy Object를 과도하게 미는 문제)에서 새로 도입된 값으로, held object가 무관한 다른 RigidBody와 접촉해 누르는 방향으로 지속 전달할 수 있는 압축력을 질량당 얼마로 제한할지 결정한다. 헤드리스 자동 검증으로 "빈손 Body Push(220N)보다 가벼운 held object가 강하게 밀지 않는가", "질량 순서(Light≤Medium≤Heavy)가 역전되지 않는가", "target 질량이 클수록 덜 밀리는가"까지 확인했다(26개 항목 3회 연속 PASS).

**사용자 승인**: `docs/TASKS.md` T076 "재오픈 결함 사용자 재검증 승인(최종)"에서 11개 항목(빈손/미접촉/Light/Medium/Heavy 밀기, 질량 순서, target 질량별 반응, 강제 추종 없음, 속도 폭주 없음, 기존 Grab 감각, 1인/2인 협동) 전부 승인되어, 현재 수치는 **사용자 승인된 프로토타입 기준값(Baseline)**으로 확정한다 — T061/T072/T074와 같은 성격이며, 여러 후보를 실측 비교하는 T068식 전용 튜닝은 아직 거치지 않았다. 완료를 막는 미해결 결함으로 취급하지 않으며, 추가 조정이 필요하다고 판단되면 별도 Task로 진행한다.

### TD-020 — 설정 슬라이더 범위·손상값 복구 범위(T079)는 실측 후보 비교 없는 초기값 (비차단, 튜닝 항목으로 유지)

`GameSettings.gd`의 `_MOUSE_SENSITIVITY_RANGE`(0.0005~0.02)·`_GAMEPAD_SENSITIVITY_RANGE`(0.5~10.0), 그리고 `SettingsPanel.tscn`의 각 슬라이더 min/max/step(마우스 감도 0.0005~0.02 step 0.0005, 게임패드 감도 0.5~10.0 step 0.5, Master Volume 0~100 step 1)은 기존 Baseline 기본값(`mouse_sensitivity=0.003`, `gamepad_look_sensitivity=2.5`)을 중심으로 여유를 둔 초기 추정값이다 — 이 범위 밖 값이 안전하게 기본값으로 복구되는지는 헤드리스 자동 검증으로 확인했으나, 범위 자체가 실제 플레이에서 "너무 좁다/너무 넓다"인지는 실측 후보 비교를 거치지 않았다.

완료를 막는 미해결 결함으로 취급하지 않는다. 사용자 수동 테스트에서 감도 슬라이더 양 끝 체감이 불편하면 범위만 조정하는 별도 Task로 진행한다.

### TD-021 — PauseMenu·SettingsPanel이 매우 작은 창 크기(900×500)에서 버튼이 잘림 (비차단)

`PauseMenu.tscn`/`SettingsPanel.tscn`은 스크롤이나 폰트 축소 없는 단순 `CenterContainer` + `VBoxContainer` 구조라, 콘텐츠 높이가 창 높이를 넘으면 위/아래 버튼이 뷰포트 밖으로 잘린다. 헤드리스 자동 검증(T079)으로 1280×720/1600×900/1920×1080/2560×1440에서는 문제 없음을 확인했으나, 900×500(매우 작은 비표준 해상도)에서는 재현됨을 2회 반복 실측으로 확인했다.

이 프로젝트의 목표 플랫폼(Windows PC, Steam)에서 900×500은 실제 지원 대상으로 보기 어려운 매우 작은 해상도라 완료를 막는 결함으로 취급하지 않는다. 필요 시 `ScrollContainer` 도입이나 최소 창 크기 제한 등을 별도 Task로 제안한다.

**T084 추가 조사**: T084에서 같은 방식(헤드리스 `root.size` 변경)의 해상도 검사를 재실행해 동일한 패턴(900×500에서만 잘림 재현)을 재확인했으나, 이어서 `DisplayServer.window_set_size()`/`window_get_size()`가 `--headless` 환경에서 사실상 동작하지 않고(`window_get_size()`가 항상 `(0,0)`), `root.get_viewport().get_visible_rect()`도 `root.size`를 바꿔도 프로젝트 기본 참조 해상도(1152×648)에 가깝게 고정된 채 반응하지 않음을 별도 진단으로 확인했다. 즉 이 프로젝트의 `canvas_items`+`expand` Stretch는 실제 창의 OS 리사이즈 이벤트로만 정상 재계산되며, 헤드리스에는 그 이벤트를 낼 실제 창이 없어 **이 항목의 헤드리스 자동 검증 자체가 구조적으로 신뢰할 수 없다**(T079·T084 두 세션 모두 같은 한계를 공유했을 가능성이 있음 — `MOUSE_MODE_CAPTURED` 헤드리스 제약과 동일한 종류의 엔진 한계, TD-014/015 계열 참고). 따라서 이 결함은 여전히 "미확정"으로 남겨 두며(있을 수도, 없을 수도 있음), 실제 창에서의 최종 확인 전까지 `ScrollContainer` 등 코드 수정은 임의로 적용하지 않는다 — 사용자 수동 테스트(900×500, 비16:9 비율 포함)로만 최종 결론이 가능하다.

### TD-022 — 절차적 효과음(T082) 8종의 주파수·길이·음량은 실측 후보 비교가 아닌 초기 추정값 (비차단, 튜닝 항목으로 유지)

`ui_select`/`ui_back`/`ui_pause_open`/`grab_success`/`grab_release`/`grab_forced_release`/`delivery_success`/`delivery_complete` 8개 절차적 효과음(`AudioManager.gd` 상단 주석에 정확한 합성 방식 기록)은 T044/T061처럼 여러 후보를 헤드리스로 비교 실측한 값이 아니라, "서로 구분되면서 거슬리지 않을 것"이라는 목표로 정한 초기 추정값(주파수 스윕 범위, 길이 55~400ms, 음량 0.22~0.32)이다. 헤드리스 자동 검증으로 "정확한 이벤트에서만 재생되는가", "성공/실패·수동/강제 해제가 서로 혼동되지 않는가", "Master Volume이 실제로 적용되는가"까지는 확인했지만, "듣기 편안한가", "너무 크거나 거슬리지 않는가" 같은 체감은 자동 검증할 수 없어 사용자 수동 플레이 후 조정이 필요할 수 있다.

## 해결됨

### TD-009 — 다인 운반을 전제하지 않은 잡기 구조 (해결, T072)

- **내용**: `GrabbableBody`(T071에서 `Package.gd`로부터 이관)의 `holder`는 단일 `CollisionObject3D` 참조이고, collision exception도 1:1 쌍으로만 관리되었다(`DESIGN_DECISIONS.md` DD-007 참고). `ROADMAP.md` v0.3.0(Fun Physics Update, 로컬 다인 협동 검토)에서 여러 명이 동시에 하나의 오브젝트를 잡는 기능을 구현하려면 이 구조 자체를 재설계해야 했다.
- **해결**: `docs/TASKS.md` T072에서 단일 `holder` 구조를 다중 `grab_connections: Dictionary` 구조로 재설계했다(`DESIGN_DECISIONS.md` DD-023). 여러 Grabber가 같은 물체를 동시에 잡고 각자의 힘을 독립적으로 계산·적용할 수 있으며, 헤드리스 검증으로 2 Grabber가 1 Grabber보다 Crate를 더 빠르게 들어올리는 것을 확인했다. **다만 이번 해결은 로컬 물리 구조에 한정된다** — 실제 온라인 멀티플레이 네트워크 동기화(입력 전송, 권한 판정, 지연 보정 등)는 여전히 미구현이며 `ROADMAP.md` v0.3.0 이후 별도 작업이 필요하다.

### TD-012 — 범용 Grabbable 물리값(T071)이 실측 후보 비교가 아닌 역산·추정값으로 결정됨 (해결, T072에서 대체)

- **내용**: `max_carry_force`(600.0)는 기존 Package `follow_acceleration(40.0)×mass(15.0)`에서 역산했고, 스윙 릴리즈의 `_MAX_SWING_SPEED`(12.0)·`_SWING_IMPULSE_GAIN`(8.0)은 여러 후보값을 헤드리스로 비교 실측하는 과정 없이 초기 추정값으로 결정되었었다.
- **해결(대체)**: 사용자 지시로 T072에서 속도 추종 방식 자체가 Force-Based Physics Grab으로 전면 교체되면서, 이 값들과 관련된 코드(`max_carry_force`, `follow_strength`, `max_follow_speed`, `_MAX_SWING_SPEED`, `_SWING_IMPULSE_GAIN`)가 전부 삭제되어 더 이상 존재하지 않는다. 튜닝 자체가 필요했던 대상이 사라졌으므로 "해결"로 분류하되, 동일한 성격의 새 미해결 항목이 TD-013으로 이어진다.

### TD-003 — 다수 Package 동시 존재 시 물리 테스트 부재 (해결, T069)

- **내용**: 현재 레벨에는 Package가 1개뿐이었다. 여러 개가 동시에 존재하는 상황(Package끼리의 충돌, 여러 개를 순차 배송)의 성능·안정성은 테스트되지 않았었다. `KNOWN_ISSUES.md` KI-005와 연결됨.
- **해결**: `docs/TASKS.md` T069에서 `PackageB`/`PackageC`를 추가해 헤드리스로 검증(55개 항목 PASS) 후 사용자 수동 테스트로 최종 승인받았다.

### TD-006 — Export 값이 "동결"되었을 뿐 최적화되지 않음 (해결, 사용자 승인)

- **내용**: T061에서 모든 export 변수를 실제 값 변경 없이 "Baseline Freeze"로 확정했다. 이는 "현재 값이 조작 불가능하거나 불안정하지 않다"는 확인이지, 최적의 조작감을 찾았다는 뜻은 아니었다. `ROADMAP.md` v0.2.0(Gameplay Expansion)의 재미 검증 과정에서 재조정될 수 있다고 기록되어 있었다.
- **해결**: `docs/TASKS.md` T068에서 확장된 환경(벽/좁은 문/환경 물리 오브젝트 포함)을 기준으로 재검증했다. 헤드리스 자동 검증으로 객관적 문제 1건(`max_follow_speed`)을 발견해 수정했고, 나머지 값은 사용자 수동 테스트에서 "밀기·잡기·운반·던지기 감각에 별도의 문제나 수치 조정 필요성이 없다"고 승인되어 그대로 유지가 확정되었다.

### TD-010 — 환경 물리 오브젝트(T064)의 물리 파라미터가 실측이 아닌 상대적 추론으로 결정됨 (해결, 사용자 승인)

- **내용**: `PhysicsBarrel`/`PhysicsCrate`/`SmallPhysicsBox`의 mass/friction/damp 값은 Package(mass 15, friction 0.7)를 기준으로 "Crate는 더 무겁게, SmallBox는 더 가볍게"라는 상대적 스케일 추론으로 결정되었고, 여러 후보값을 헤드리스로 실측 비교하는 과정은 거치지 않았었다.
- **해결**: `docs/TASKS.md` T068의 사용자 수동 테스트에서 Crate 연속 밀기, Barrel 굴리기, SmallBox 밀기를 포함한 밀기 감각 전체가 승인되어, mass/friction/damp 값 그대로 유지가 확정되었다. 초기값이 실측 비교가 아닌 상대적 추론이었다는 이력은 참고용으로 남겨 둔다.

### TD-011 — 좁은 문(T066) 폭이 실측 후보 비교가 아닌 단일 추론값으로 결정됨 (해결, 사용자 승인)

- **내용**: `NarrowDoorwayTestArea`의 clear width(1.4m)는 Player capsule 지름(1.0m)·Package 폭(0.8m) 실측 크기를 근거로 "Player 혼자는 여유 있게, 대각선 접근 시 Package가 걸릴 수 있게"라는 단일 목표값으로 정해졌다. T044(`throw_impulse_strength`, 8개 후보 실측 비교)나 T022 계단 재작업(단일 단 높이를 0.18m/0.19m 경계까지 실측)과 달리, 여러 폭 후보를 헤드리스로 비교 측정하지는 않았다.
- **해결**: 사용자 수동 테스트에서 "좁은 문 통과 및 문틀 충돌 동작 정상"으로 확인되어, 1.4m 값 그대로 승인되었다(값 조정 없음). 초기값이 후보 비교가 아닌 단일 추론이었다는 이력은 참고용으로 남겨 둔다.
