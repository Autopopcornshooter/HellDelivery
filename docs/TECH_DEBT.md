# TECH_DEBT.md

이 문서는 **현재는 문제가 아니지만** 프로젝트가 성장하면 개선이 필요해질 내용을 기록한다.

**역할**: 나중에 개선할 것. 지금 당장 고장난 것은 `KNOWN_ISSUES.md`에 기록한다. 이 문서의 항목은 버그가 아니다 — 지금 상태로도 MVP-1은 정상 동작한다.

---

### TD-001 — 디버그 로그 제거

`Player.gd`의 `_detected_package`(`# DEBUG` 표시)와 `"Package detected"`/`"Package lost"` `print()`는 T041에서 감지 로직을 확인하기 위해 추가되었다. 정식 빌드 전 제거하거나, 필요하다면 로깅 시스템으로 정리한다.

### TD-002 — 물리 파라미터가 체계적 설계가 아닌 실측 재탐색으로 결정됨

`throw_impulse_strength`(12.0 → 200.0), `push_force`(8.0 → 40.0 → 220.0) 등은 질량/마찰/댐핑 공식에서 역산한 것이 아니라 여러 값을 실측 테스트하며 목표 체감(비행거리, 밀림 거리)에 맞춰 경험적으로 조정되었다. 콘텐츠가 늘어나(예: 여러 종류의 택배, 서로 다른 질량) 값이 더 많아지면, 질량/마찰 기반 공식으로 자동 계산하는 방식을 검토한다.

### TD-003 — 다수 Package 동시 존재 시 물리 테스트 부재

현재 레벨에는 Package가 1개뿐이다. 여러 개가 동시에 존재하는 상황(Package끼리의 충돌, 여러 개를 순차 배송)의 성능·안정성은 아직 테스트되지 않았다. `KNOWN_ISSUES.md` KI-005와 연결됨.

### TD-004 — 프로토타입 레벨 지오메트리를 정식 레벨로 교체 필요

`PrototypeLevel.tscn`의 지형(`Floor`, `Stairs`, `Ramp`)은 모두 `BoxShape3D`/`BoxMesh` 플레이스홀더다. 특히 계단은 실제 플레이 검증(T045) 중 발견된 문제(0.4m 단 높이가 걸어서 오를 수 없는 수준) 때문에 13단(단 높이 0.15m, 단 깊이 0.385m)으로 재작업되었는데, 이 수치는 "일단 통과 가능하게 만든" 값이지 미술적으로 다듬어진 정식 계단 형상이 아니다. 정식 맵(v0.5.0 Content Expansion) 제작 시 처음부터 아트/레벨 디자인 기준으로 재설계해야 한다.

### TD-005 — 리소스가 씬 파일에 인라인으로 정의됨

`Player.tscn`, `Package.tscn`, `PrototypeLevel.tscn` 등의 `CollisionShape3D`/`MeshInstance3D`에 쓰이는 `BoxShape3D`, `CapsuleShape3D`, `BoxMesh` 등이 각 씬 파일 내부에 `sub_resource`로 인라인 정의되어 있고, 별도의 재사용 가능한 `.tres` 리소스 파일로 분리되어 있지 않다. 씬 수가 적은 MVP-1 단계에서는 문제가 없지만, 여러 종류의 택배·여러 레벨이 같은 형태를 공유하게 되면 공통 리소스로 추출하는 것을 검토한다.

### TD-006 — Export 값이 "동결"되었을 뿐 최적화되지 않음

T061에서 모든 export 변수를 실제 값 변경 없이 "Baseline Freeze"로 확정했다. 이는 "현재 값이 조작 불가능하거나 불안정하지 않다"는 확인이지, 최적의 조작감을 찾았다는 뜻은 아니다. `ROADMAP.md` v0.2.0(Gameplay Expansion)의 재미 검증 과정에서 재조정될 수 있다.

### TD-007 — 성능 최적화 미실시

현재 씬 규모(노드 수, 물리 바디 수)가 작아 성능이 문제된 적이 없어 별도 최적화를 하지 않았다. 콘텐츠가 늘어나면(여러 Package, 정식 맵, 온라인 동기화) 프로파일링과 최적화가 필요해질 것이다.

### TD-008 — 헤드리스 검증 스크립트가 임시 파일로만 존재

개발 과정에서 사용한 헤드리스 `SceneTree` 기반 검증 스크립트(`_tmp_*.gd`)는 매 작업마다 새로 작성하고 확인 후 삭제하는 방식으로 운용되었다(`CLAUDE.md`의 임시 코드 정리 원칙에 따름). 재사용 가능한 회귀 테스트 스위트로 정리되어 있지 않아, 이후 변경 시 동일한 검증을 처음부터 다시 작성해야 한다. 프로젝트 규모가 커지면 정식 테스트 스위트 도입을 검토한다.

### TD-009 — 다인 운반을 전제하지 않은 잡기 구조

`Package.gd`의 `holder`는 단일 `CollisionObject3D` 참조이고, collision exception도 Package-holder 1:1 쌍으로만 관리된다(`DESIGN_DECISIONS.md` DD-007 참고). `ROADMAP.md` v0.3.0(Fun Physics Update, 로컬 다인 협동 검토)에서 여러 명이 동시에 하나의 Package를 잡는 기능을 구현하려면 이 구조 자체를 재설계해야 한다.

### TD-010 — 환경 물리 오브젝트(T064)의 물리 파라미터가 실측이 아닌 상대적 추론으로 결정됨

`PhysicsBarrel`/`PhysicsCrate`/`SmallPhysicsBox`의 mass/friction/damp 값은 Package(mass 15, friction 0.7)를 기준으로 "Crate는 더 무겁게, SmallBox는 더 가볍게"라는 상대적 스케일 추론으로 결정되었고, T044(`throw_impulse_strength`)·T061(Baseline Freeze)처럼 여러 후보값을 헤드리스로 실측 비교하는 과정은 거치지 않았다. 헤드리스 자동 검증으로 "관통/NaN/폭발적 가속이 없음"까지는 확인했지만, "구르는 느낌"·"적층이 자연스러운지"·"밀림 강도가 적절한지" 같은 체감은 자동 검증할 수 없어 사용자 수동 플레이 후 조정이 필요할 수 있다. `ROADMAP.md` v0.2.0 EPIC-02(Physics Feel Tuning) 범위에서 함께 재검토할 후보.
